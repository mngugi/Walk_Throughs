# PNG Decompression Bomb: Analysis and Defensive Notes

## Image Dimensions

The first four bytes after `IHDR` are the width:

```
00 00 75 30
```

Interpreted as a big-endian integer:

```
0x7530 = 30000
```

The next four bytes are the height:

```
00 00 4e 20
```

Interpreted as a big-endian integer:

```
0x4e20 = 20000
```

Therefore:

- **Width** = 30,000 pixels
- **Height** = 20,000 pixels

The file describes an image measuring:

**30,000 × 20,000 pixels**

or:

**600,000,000 pixels**

## The tEXt Chunk

The PNG also contains the following text metadata:

```
preview 64x64 generated by avatar-resizer 2.1
```

This appears in a `tEXt` chunk.

However, the `64x64` value is **not** the actual image dimensions.

It is simply free-form metadata written into the PNG by another tool.

The actual dimensions are contained in the authoritative PNG `IHDR` header:

**30000 × 20000**

Therefore:

> The `64x64` text is metadata about a preview, not the dimensions of the PNG itself.

## Memory Implications

The image contains:

```
30,000 × 20,000
```

pixels.

Therefore:

```
30,000 × 20,000 = 600,000,000 pixels
```

If the image is decoded as RGBA with 8 bits per channel:

```
4 bytes per pixel
```

The raw pixel buffer requires approximately:

```
600,000,000 × 4
= 2,400,000,000 bytes
```

That is approximately:

- **2.4 GB**
- or about **2.24 GiB**

for a single full-canvas RGBA allocation.

### Important

The actual peak memory consumption can be substantially larger.

Depending on the image library and processing pipeline, additional memory may be required for:

- A second decoded image buffer
- Scanline buffers
- PNG filtering
- Intermediate resize buffers
- Color-space conversion
- Temporary copies
- Output buffers

Consequently, a worker with a memory limit of 512 MB or 1 GB could fail before the image is successfully resized.

## Why the File Can Be So Small

The interesting part is that the PNG file itself can be very small compared with the amount of memory required to decode it.

The important distinction is:

```
Compressed file size
        ≠
Decoded image size
```

A highly compressible image can contain hundreds of millions of pixels while occupying relatively little space on disk.

For example:

```
Compressed PNG
        ↓
      ~46 KB
        ↓
PNG decompression
        ↓
600,000,000 pixels
        ↓
~2.4 GB RGBA buffer
```

This creates a massive expansion ratio.

That asymmetry is what makes decompression bombs dangerous:

> The attacker sends a relatively small payload, while the receiver may be forced to allocate a very large amount of memory to process it.

## Why the 64x64 Metadata Is Interesting

The embedded text:

```
preview 64x64 generated by avatar-resizer 2.1
```

creates an interesting discrepancy.

A naive scanner or application might encounter:

```
64x64
```

and incorrectly assume that the image is small.

But the actual PNG header says:

```
30000 × 20000
```

The two values describe different things:

| Field | Value | Meaning |
|---|---|---|
| PNG IHDR width | 30000 | Actual image width |
| PNG IHDR height | 20000 | Actual image height |
| tEXt metadata | 64x64 | Description of a preview |
| Raw pixel count | 600,000,000 | Actual number of pixels |

The important security lesson is:

> Free-form metadata should never be treated as authoritative image dimensions.

## The Security Mechanism

The core issue is that the PNG header contains **self-reported dimensions**.

The decoder must read the `IHDR` information before it can correctly interpret the image data.

Therefore, the processing sequence is conceptually:

```
Receive PNG
    ↓
Read PNG signature
    ↓
Read IHDR
    ↓
Read width and height
    ↓
Calculate required resources
    ↓
Allocate / decode image
```

If the application does not impose limits after reading the header, an attacker can provide dimensions such as:

```
30000 × 20000
```

or potentially much larger values.

The danger is therefore not necessarily corruption of the file.

The file can be a perfectly valid PNG.

The problem is that the dimensions contained in the file can cause the application to consume excessive resources.

## Generalizable Security Lesson

This is an example of a broader class of **resource-exhaustion vulnerabilities**.

The same pattern can appear in many formats.

Examples include:

- `Content-Length` versus the actual incoming stream
- ZIP archives claiming enormous uncompressed sizes
- GZIP streams with extreme compression ratios
- Image width and height fields
- Image metadata such as EXIF dimensions
- SVG dimensions and `viewBox`
- Video container metadata
- PDF object structures
- Archive nesting
- Recursive decompression

The common pattern is:

```
Untrusted input
      ↓
Metadata declares resource requirements
      ↓
Application trusts metadata
      ↓
Large allocation / computation
      ↓
Resource exhaustion
```

## The Defensive Pattern

The application should validate dimensions **before** allocating memory.

Conceptually:

```
Read image header
      ↓
Extract width and height
      ↓
Validate width
      ↓
Validate height
      ↓
Calculate width × height
      ↓
Compare against maximum
      ↓
Reject if limit is exceeded
      ↓
Only then allocate/decode
```

For example:

```python
MAX_PIXELS = 50_000_000

if width * height > MAX_PIXELS:
    reject_image()
```

The exact limit should depend on the application's legitimate workload.

The important principle is:

> Validate resource requirements before performing the expensive operation.

## Example Defensive Calculation

Suppose an application allows a maximum of:

```
50,000,000 pixels
```

The submitted image declares:

```
width  = 30,000
height = 20,000
```

Calculate:

```
30,000 × 20,000
= 600,000,000 pixels
```

Compare:

```
600,000,000 > 50,000,000
```

Therefore:

```
REJECT
```

The application can reject the image before allocating a multi-gigabyte pixel buffer.

## Why File Size Alone Is Not Enough

A common mistake is to enforce only a maximum upload size:

```
MAX_FILE_SIZE = 10 MB
```

That does **not** necessarily protect against decompression bombs.

For example:

```
PNG file:
46 KB
```

but:

```
Decoded image:
600,000,000 pixels
```

Therefore:

```
46 KB upload
        ↓
2.4 GB decoded RGBA buffer
```

A small file can therefore represent a very large computational or memory workload.

A secure image-processing pipeline should consider both:

- **Compressed size**
- and **decoded resource requirements**

## The Deeper Security Principle

This case illustrates a fundamental rule in secure systems design:

> **Untrusted metadata is still untrusted input.**

The fact that information appears in a file header does not make it trustworthy.

Likewise, the fact that information appears in a text metadata field does not make it authoritative.

Every externally supplied value should be treated as attacker-controlled until it has passed appropriate validation.

In this case:

```
IHDR dimensions
        ↓
Untrusted input
        ↓
Validate bounds
        ↓
Calculate resource requirements
        ↓
Only then allocate memory
```

## The Key Observation

Nothing in the file necessarily needs to be corrupted.

The PNG can be structurally valid.

The danger comes from the relationship between:

- **Small compressed representation**
- and **huge decoded representation**

The critical values are:

| Property | Value |
|---|---|
| Width | 30,000 |
| Height | 20,000 |
| Pixels | 600,000,000 |
| RGBA memory | ~2.4 GB |

The `64x64` string in the `tEXt` chunk does not change those dimensions.

It is simply metadata describing a preview.

## Conclusion

The important lesson from this PNG is not merely that the image is large.

It is that **compressed size and computational cost are different security properties**.

A file can be:

- **small on disk**

while being:

- **enormous in memory** after decompression.

Therefore, secure image processing should validate:

- File size
- Width
- Height
- Pixel count
- Expected memory consumption
- Processing limits

before allowing the decoder or image-processing pipeline to perform expensive work.

The line that summarizes the entire case is:

> **Nothing in this file needs to be corrupt or malformed; it is an ordinary PNG that declares something enormous in a field the application failed to validate.**
