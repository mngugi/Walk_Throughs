
### How It Works: Known-Plaintext Attack Against Repeating-Key XOR

XOR is its own inverse and operates byte by byte. This means ciphertext XOR plaintext returns the key where the guessed plaintext aligns with the actual plaintext.

This is known as a **known-plaintext attack**, and the process of testing a guessed plaintext fragment is called **crib dragging**.

The crib in this challenge is readily available because every environment file generated by the tool begins with `ENVIRONMENT=`, a twelve-character string. XORing the decoded ciphertext bytes with this string recovers the first twelve characters of the output as `PLOVERPLOVER`. This reveals a six-letter repeating key, `PLOVER`, written twice. The repetition confirms that the guess is correct.

Everything after position twelve is not recovered by this particular crib calculation because the known plaintext ends there. However, once the repeating key has been identified, it can be applied to the entire ciphertext to decrypt the complete file.

Using the key `PLOVER`, the encrypted file decodes into a readable environment configuration containing `DB_PASS=Halyard-Spindle-41` on the fourth line.

## Why the Attack Works

The fundamental XOR relationship is:

```text
C = P XOR K
```

Where:

- `C` is the ciphertext.
- `P` is the plaintext.
- `K` is the encryption key.

Because XOR is its own inverse:

```text
K = C XOR P
```

When the plaintext is known or can be accurately guessed, the corresponding key bytes can be recovered directly. If the encryption uses a repeating key, the recovered bytes reveal the repeating pattern.

## What Was Not Needed

The attack did not require brute force, frequency analysis, or an exhaustive search for the encryption key. Instead, it exploited predictable plaintext and the mathematical properties of XOR.

A repeating-key XOR cipher reveals its key wherever an attacker can correctly guess the corresponding plaintext. Configuration files are particularly vulnerable because their formats often contain predictable field names and delimiters.

The same principle applies to other file and protocol formats, including:

- HTTP response headers, such as `HTTP/1.1`.
- PNG file signatures.
- ZIP file headers.
- JSON documents beginning with predictable structures, such as `{`.

## Security Lesson

Repeating-key XOR is not secure encryption for protecting sensitive configuration files. Predictable plaintext can expose the repeating key, allowing the entire ciphertext to be decrypted.

The key length does not provide meaningful protection when the attacker knows enough plaintext to recover the repeating pattern. A key shorter than the known plaintext is particularly vulnerable because the recovered bytes can expose one or more complete repetitions of the key.

Sensitive environment files should instead be protected using established authenticated encryption algorithms, secure key management, and appropriate access controls.

# Explicit Decryption Steps: Repeating-Key XOR

The challenge provides a hexadecimal ciphertext:

Each pair of hexadecimal digits represents one ciphertext byte.

For example:

```text
15 -> 00010101
02 -> 00000010
19 -> 00011001
1f -> 00011111
```

The ciphertext must first be decoded from hexadecimal into bytes before applying XOR.

## Step 2: Identify the Known Plaintext

The mission briefing states that every environment file begins with:

```text
ENVIRONMENT=
```

This is the known plaintext, also called a *crib*.

Its ASCII hexadecimal representation is:

```text
45 4e 56 49 52 4f 4e 4d 45 4e 54 3d
```

There are 12 characters, so there are 12 known plaintext bytes.

## Step 3: Apply the XOR Equation

The encryption relationship is:

```text
C = P XOR K
```

Where:

- `C` = ciphertext byte.
- `P` = plaintext byte.
- `K` = key byte.

XOR is its own inverse, so:

```text
K = C XOR P
```

This means that each known plaintext byte can be XORed with its corresponding ciphertext byte to recover the key byte.

## Step 4: Recover the First Key Bytes

The following table shows the first six byte calculations.

| Position | Ciphertext (hex) | Plaintext | Plaintext (hex) | XOR result |
|---:|---|---|---|---|
| 1 | `15` | `E` | `45` | `50` |
| 2 | `02` | `N` | `4e` | `4c` |
| 3 | `19` | `V` | `56` | `4f` |
| 4 | `1f` | `I` | `49` | `56` |
| 5 | `17` | `R` | `52` | `45` |
| 6 | `1d` | `O` | `4f` | `52` |

The resulting hexadecimal bytes are:

```text
50 4c 4f 56 45 52
```

Converting those bytes to ASCII gives:

```text
P L O V E R
```

Therefore, the recovered six-byte key is:

```text
PLOVER
```

## Step 5: Verify the Repeating Key

The key has six characters:

```text
PLOVER
```

A repeating-key XOR cipher reuses these six bytes cyclically. The first 12 key characters are therefore:

```text
PLOVERPLOVER
```

The known plaintext is 12 bytes long, so it allows us to recover two repetitions of the key.

The full 12-byte XOR calculation gives:

```text
Recovered key bytes (hex):
50 4c 4f 56 45 52 50 4c 4f 56 45 52

Recovered key (ASCII):
PLOVERPLOVER
```

This repetition is strong evidence that the crib is correct.

## Step 6: Decrypt the Entire Ciphertext

Recovering the key is only the first stage. To decrypt the whole file, XOR every ciphertext byte with the corresponding byte of the repeating key.

The key-index rule is:

```text
key_index = ciphertext_position MOD 6
```

Using zero-based positions, the key bytes are selected as follows:

| Ciphertext position | Key character |
|---:|---|
| 0 | `P` |
| 1 | `L` |
| 2 | `O` |
| 3 | `V` |
| 4 | `E` |
| 5 | `R` |
| 6 | `P` |
| 7 | `L` |

The sequence continues until every ciphertext byte has been processed.

The decryption equation is:

```text
P[i] = C[i] XOR K[i MOD 6]
```

Here, `P[i]` is the recovered plaintext byte at position `i`, `C[i]` is the ciphertext byte, and `K` is the six-byte key.

## Step 7: Recover the Database Password

After applying the repeating key to the entire ciphertext, the readable environment configuration reveals the database password in the `DB_PASS` field.

The reported password is:

```text
Halyard-Spindle-41
```

## Step 8: Understand the Security Weakness

The attack succeeds because the encryption uses a repeating key and the plaintext contains predictable data.

The attacker does not need to search every possible key. Knowing the plaintext allows the corresponding key bytes to be calculated directly.

This weakness applies to predictable file headers, configuration fields, and protocol messages. Repeating-key XOR should not be used to protect sensitive data; authenticated encryption and proper key management are required instead.

## Step 9: Reproduce the Attack with Python
The following code demonstrates the complete procedure using the ciphertext supplied in the challenge.

```python
ciphertext_hex = (
    "1502191f171d1e010a18116f203e20323031242520384f"
    "161213071916066d202a32223722612b346b3b3e382a242b"
    "333c623b3e2a203e2e3a243c7c35342e3b353e35460b141a"
    "0703091d6b3624331323332135353e4512070d000d1c0578"
    "1a3120363737367d1f3f3f2b363c2962627458140e10060a"
    "0004717a6276605a"
)

ciphertext = bytes.fromhex(ciphertext_hex)

# Step 1: Define the known plaintext.
crib = b"ENVIRONMENT="

# Step 2: Recover the corresponding key bytes.
key_bytes = bytes(
    c ^ p for c, p in zip(ciphertext[:len(crib)], crib)
)

print("Recovered key bytes:", key_bytes)
print("Recovered key:", key_bytes.decode())

# Step 3: Verify the six-byte repeating key.
key = key_bytes[:6]
assert key_bytes == (key * 2)

# Step 4: Decrypt the complete ciphertext.
plaintext = bytes(
    c ^ key[i % len(key)]
    for i, c in enumerate(ciphertext)
)

print("\nDecrypted environment file:")
print(plaintext.decode("utf-8", errors="replace"))

```
## Step 10: Understand One XOR Calculation at the Bit Level
Take the first ciphertext byte, 15 in hexadecimal, and the first known plaintext byte, E, which is 45 in hexadecimal.

```text
Ciphertext:  15 = 00010101
Plaintext:   45 = 01000101
                  -------- XOR
Key byte:    50 = 01010000

```
> The resulting hexadecimal value 50 represents the ASCII character P.
> Repeating this operation across the first six bytes yields PLOVER. The key then repeats every six bytes throughout the > ciphertext.
**Final lesson:** the known plaintext reveals the key through XOR arithmetic; the repeating key decrypts the complete message. These are two distinct stages of the same attack.
